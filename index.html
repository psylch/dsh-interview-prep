一句话：dsh 是 DeepSeek 开源（MIT）的 agent harness：模型接入、工具、会话日志、审批、沙箱、agent 主循环和界面全是 Cordis 插件，可以直接拿来干活，也可以拆了重组成自己的产品。官方定位仍是「开发者预览，会有破坏性变更」。

四个内置预设：标准（完整编码 agent）、极简（只有 bash + 编辑器，适合跑基准）、PTC（模型写代码去调工具，一次调用替代多轮往返）、创造（agent 能检查运行时、写插件、装插件）。（The New Stack）

一个 turn 怎么走（场景：「改代码并跑测试」）

  1. 输入进 inbox。三种中途输入：steer（下一步生效并唤醒）、followup（下一轮）、inject（下一步但不唤醒，用于后台事实）。pending 输入持久化，不只是 UI 队列。packages/core/agent-loop/src/agent.ts:154、inbox.ts:27
  2. 组 prompt、选模型。插件可在 agent/pre-step 改写或拒绝。agent.ts:307-331
  3. 调模型前先落盘（checkpoint）。llm/stream 中间件先 sessions.flush()。packages/session/session-checkpoint-policy/src/index.ts:64
  4. 工具调用：先记 call，再审批，再 guard。人批准后仍要过只能“拒绝”的 guard；缺应答者一律拒绝（fail closed）。packages/core/tools/src/index.ts:1513-1527
  5. 顶层工具执行前再 checkpoint；嵌套调用不单独落盘。session-checkpoint-policy/src/index.ts:70-71
  6. 结果追加日志，上下文压力大时在下一次请求前压缩（压缩只改“模型看到的视图”，原始日志保留）。packages/compaction/compaction-basic/src/index.ts:158,291

8 个关键设计选择

设计白话边界（面试别说过头）
一切皆插件连主循环都能换；加功能是“挂插件”，卸载时注册的东西自动撤销插件生命周期本身成了复杂度来源；团队规则写着“Plugins, not loop changes”（AGENTS.md:138）
日志即真相“模型看到的 ⟺ 日志里有的”（AGENTS.md:137）能重建已提交事实，不能重建落盘前崩掉的流
崩溃恢复重启后给中断的调用补“interrupted/结果未知”，不盲目重放副作用恢复的是对话历史，不是 exactly-once 执行。packages/core/agent-loop/src/index.ts:876-891、packages/core/session/src/repair.ts:34
PTC 脚本内调用脚本里每个子调用都有日志记录（tool/ptc-dispatch）但不能从脚本中间续跑：不保存变量、await 位置。packages/core/tools/src/ptc.ts:587-614、packages/ptc-runtime/ptc-runtime/README.zh.md:144
单写者锁POSIX flock / Windows 内核信号量，防两个进程同时续写一个会话是互斥锁，不是任务租约。packages/session/session-persistence-jsonl/src/lease.ts:14
权限三段式文件沙箱模式（只读/工作区可写/全开）× 审批策略（ask/never）× guard沙箱只管文件，不管网络和进程可见性（docs/subsystems/sandbox.zh.md:5-11）
长任务四件套goal（干到完成或卡住）、schedule（定时）、jobs（后台命令）、workflow（脚本编排子 agent）见 Tab 5 判定表：审批等待和后台进程都不跨重启
子 agent / Agent Teamspawn/fork 子 agent；可把 Claude Code、Codex 当执行后端；实验性 Team 有任务 DAG 和 inbox外部后端只回最终答案，内部过程不进父日志

它要解决的两个问题（用 harness 场景说）

维度问的是翻车场景
时间可组合性我卸掉一个插件，它留下的东西能不能收干净？卸了检索插件，但它注册的事件监听还在跑；重装后又多一份注册。只能靠重启进程清理，代价是丢掉缓存、连接和进行中的任务。
空间可组合性我依赖的服务换了/没了，谁来协调？管理员换了搜索后端，插件还拿着旧对象的引用；或旧服务先退出，插件的清理代码却还需要它。

两者必须一起解决：撤销插件要用到旧服务，旧服务何时能退又取决于插件是否撤完（§3.1.3、§4.3.3）。

核心设计（白话）

  • 可逆副作用（revertible effects）：每做一件事就同时交出“怎么撤销”，运行时替你保管，卸载时倒序执行。ctx.effect(() => { const t = tools.add(...); return () => tools.remove(t) })
  • 响应式协效（reactive coeffects）：插件声明“我需要 tools 和 searchBackend”；依赖到齐才激活，依赖没了先停用，换了新的再重新激活。
  • 上下文范式（context paradigm）：“我需要什么”和“我改了什么”走同一个 context，所以“父插件卸载时子插件跟着退”复用同一机制。
  • 组件演算 + 元理论：证明了在前提成立时：撤销精确（只撤自己的贡献）、顺序正确（依赖先就绪、提供方活到消费方清理完）、一定会停下来、不同交错顺序得到等价结果（§4.3，Theorem 64–80）。
  • 实现：Cordis 核心库 + 声明式 loader（配置差异只做局部操作）+ 热模块替换。在 dsh 里对应 vendor/cordis/src/fiber.ts:356,418、vendor/loader/src/config/group.ts:48、vendor/hmr/src/index.ts:199；工具注册本身就是 effect：packages/core/tools/src/index.ts:1071。

证据有多硬

材料能说明不能说明
形式化证明前提成立时的语义保证运行开销、热更新延迟、agent 任务成功率
Koishi 生态：4 年、4000+ 社区插件（Cordis v3）这种组合模式能撑起真实生态不是 v4 的实测，不是压力测试

作者明说案例是观察性的，测量抽象开销和开发者生产力留作未来工作（§5.3）。

论文里和 agent harness 直接相关的话

“Modern software — from plugin systems to self-evolving agent harnesses — increasingly requires dynamic composition…”（摘要）
“A future harness may generate and deploy modifications to its own components while continuously serving requests.”（§1.2.2）
“…a compelling direction for future validation is self-evolving agent harnesses… where an AI agent generates and replaces its own harness components continuously and with little human oversight.”（§8）

注意都是 “future / may / would validate”。dsh 的创造模式是这个方向的第一个产品形态；但当前源码里模型可用的 Cordis 工具只读（cordis_inspect_list/query），持久扩展要走插件管理器安装（packages/extensions/tool-cordis/src/index.ts:21）。

作者承认的局限

  • 逆操作写得对不对是插件作者的义务，运行时不验证（§5.1.1）。
  • 已经发到网络、写给别人看的东西撤不回；补偿（如退款）不继承全部定理（§6.1）。
  • context 权限检查挡不住恶意插件，真沙箱需要进程/容器边界（§6.3）。
  • 跨包接口漂移、同名 key 冲突仍是开放问题（§6.6）。

B. 你的候选增量：对照源码和社区

候选dsh 现状（源码）社区有没有要判断

E. 面试里可以说/问的话

1. 表达判断（不是让他们照抄谁）：“我对 agent 的判断是终局是人——一个能稳定、持续服务别人的人。所以我看 harness 会问：它能不能像员工一样长期在岗？dsh 在中途插话、单写者锁、不盲目重试这些地方已经很扎实；我看到的缺口是汇报线：需要拍板、做完了、卡住了，这些事件已经在日志里，但还出不去。社区里已经有人自己做 ntfy、PWA、安卓客户端来补，这说明需求是真的。”

3. 问度量：“JD 里写要衡量 agent 是否在更多场景下更深入地帮到更多人。V4.1-Flash-1017 说专门为 DSH 优化过，你们内部用什么指标判断这次优化成功了？社区有人自测说 token 更多，这类外部信号怎么进到评测里？”

4. 问生态：“60% 的用户用了第三方插件，同时升级报错是社区第一大话题。你们会怎么权衡快速迭代和插件 API 稳定？有没有在度量升级后的插件崩溃率？”
